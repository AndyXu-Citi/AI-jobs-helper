# AI-jobs-helper 架构评审与改进建议

> 评审日期：2026-08-14
> 评审范围：`src/`（agent / rag / web / sources / mcp_server）、`scripts/`、`src/db_manager.py`、`src/db_config.py`
> 方法：通读核心模块源码，按"分层 — 亮点 — 问题 — 路线图"结构化输出，问题均附 `file:line` 证据。

## 1. 架构分层总览

| 层 | 实现 | 职责 |
|---|---|---|
| 表现层 | `src/web/static/index.html` | 5 Tab 单页，原生 HTML/JS，SSE 消费流式结果 |
| 服务/API 层 | `src/web/app.py`（FastAPI，913 行） | 9+ REST/SSE 端点，直接内联 SQL + Prompt + 内存会话态 |
| 智能编排层 | `src/agent/{graph,nodes,tools}.py` | LangGraph 5 节点 DAG + 反思循环；`processor.LLMProcessor` 清洗 |
| RAG 原语层 | `src/rag/{embedder,vector_store}.py` | bge-m3 1024d 向量化；FAISS 索引（.faiss + .pkl） |
| 数据层 | `src/db_manager.py` + `src/db_config.py` | MySQL 5 表；`BaseSource` 采集抽象（Boss/arXiv/Bilibili） |
| 外部 | DeepSeek（LLM）、Boss/arXiv/Bilibili（数据源） | — |

整体是**清晰的单向分层 + 插件式采集抽象**，方向对，下面指出的都是"规模上来/要长期维护"时才暴露的工程债。

## 2. 架构亮点（建议保留）

- **采集抽象做对了**：`BaseSource`（`sources/base.py:27`）用 ABC 统一 `fetch_new_urls()`，新增源零侵入 Monitor/DBManager，是项目里最干净的抽象。
- **Agent 反思循环有防死锁设计**：`nodes.py:74` `MAX_RETRY_ROUNDS=3` + `reflect()` 强制"必须给出新关键词才算 retry"（`nodes.py:390-399`），避免了 LLM 换词空转烧 token。
- **确定性 vs LLM 节点分离清晰**：`retrieve`/`filter` 不调 LLM（`nodes.py:209`/`249` 注释明确），省 token 也利于复现。
- **Bad Case 闭环有雏形**：`agent_runs` 表 + `status` 三态（unreviewed/good/bad），零结果自动标 bad。
- **配置不硬编码密钥**：统一走 `.env`（`db_config.py` / `nodes.py:_llm`）。
- **全链路 trace**：每个节点往 `state["trace"]` 追加日志，可回放 Agent 走了哪条路。

## 3. 主要问题（按优先级）

### P0 — 正确性 / 数据质量

**3.1 `build_embed_text` 读错字段层级，Boss 召回质量存疑**
`scripts/index_final_results.py:54-72` 拼 embedding 文本时读的是 `structured` 的**顶层** `summary/key_points/tags`，但 Boss 数据实际嵌套在 `_boss` 下（检索时 `_build_record` 才读 `_boss`）。若 Boss 顶层这些字段为空，embedding 文本就只剩标题 → 语义检索退化为"标题匹配"。
→ **修法**：改为读 `_boss.post_description` + `_boss.skills`（enrich 脚本注释也要求 postDescription 进 embed）。这是换 Milvus 前必须做的，否则只是把"召回差"搬到新库。

**3.2 向量库 `text` 字段写入却永不返回（死存储）**
`vector_store.py:135-141` upsert 把 `text` 存进元数据，但 `search()` 只回 `url/title/score`（`vector_store.py:204-209`），详情永远靠回查 MySQL。存储冗余，且容易让人误以为向量库里有正文可用。
→ 可接受，但建议文档写明"向量库仅存检索入口"。

### P1 — 架构耦合 / 重复实现

**3.3 同一张表两套实现：`BadCaseStore` 与 `DBManager` 重复**
`bad_case_store.py:82-203` 的 `record_run/mark/list/stats` 与 `db_manager.py:363-497` 的 `record_agent_run/mark_agent_run/list_agent_runs/agent_run_stats` 做的是**完全相同**的事，代码路径发散、易不一致。
→ **修法**：保留 `DBManager` 作为唯一数据访问层，`BadCaseStore` 直接委托或删除（web/MCP 调用方统一走 DBManager）。

**3.4 LLM 客户端三套不一致**
- `nodes.py:_llm()`：`langchain_openai.ChatOpenAI`（temperature=0.2, timeout=180, max_retries=2）
- `processor.py:36`：`openai.OpenAI` 原生客户端
- `mcp_server` / `app.py` interview 端点：又各自构造
超时、温度、重试策略各不相同，难以统一治理（限流、可观测、降级）。
→ **修法**：抽 `src/llm/client.py` 单一 `LLMClient`，配置驱动参数，全局复用。

**3.5 `app.py` 单文件 913 行，路由/SQL/Prompt/会话态全耦合**
端点里直接写 SQL（`_load_all_structured` `app.py:334`、`_llm_extract_and_cache` `app.py:389`）、内联 Prompt、面试会话存进程字典（`interview_sessions`）。
→ **修法**：拆 `routers/`（jobs / chat / match / interview / report），SQL 下沉到 repository，Prompt 收口到 `prompts.py`，会话态外置。

**3.6 数据库连接无池化，且每次调用重连**
`db_config.py:77` 每次 `get_connection()` 都 `mysql.connector.connect()`。高并发 Web 下每请求一连接，且 `tools.py` 检索路径每次调用都 `HuggingFaceEmbedder()` + `VectorStore()`（`tools.py:78-79`）——后者每次从磁盘重读 FAISS 索引。
→ **修法**：`mysql.connector.pooling` 连接池；`VectorStore` 改为进程级单例（lazy load 一次）。

### P2 — 可维护性 / 运维

**3.7 同步 LLM 调用阻塞事件循环**
`/api/chat`（`app.py:157`）是 `async def` 却调同步 `find_jobs()`（内部阻塞 LLM 调用）。单 worker 下并发请求会串行化。
→ **修法**：Agent 跑在 `run_in_threadpool`，或节点改 `async` + `await llm.ainvoke`。

**3.8 FAISS 删除是 O(n) 全量重建 + 非线程安全**
`vector_store.py:_rebuild_index` upsert 同 url 触发整表 reconstruct；索引变更在 GIL 下非原子，enrich 与 Web 并发会竞态。
→ **修法**：迁移到 Milvus（你已在做）天然解决；过渡期加 `threading.Lock` 守卫。

**3.9 面试会话仅存内存**
`/api/interview/sessions` 从进程字典读，重启即丢、多 worker 不共享。
→ **修法**：持久化到 MySQL（可复用 `agent_runs` 思路加 `interview_runs` 表）。

**3.10 缺健康检查 / 指标 / 鉴权**
无 `/healthz`、无 LLM 延迟/错误率指标；端点对外开放，部署后任何人可 POST `/api/chat` 烧 DeepSeek token。
→ **修法**：加 health 端点 + 简单 API Key 中间件（若暴露公网）。

**3.11 文档与代码漂移**
README 仍写 Milvus/Ollama/火山引擎，实际是 FAISS/HF/DeepSeek（已知，但属于架构交付物的一部分）。
→ **修法**：对齐 README（可随时帮你改）。

**3.12 Bad Case 闭环未闭合到 UI**
`agent_runs` 有数据但 Web 没有 replay 入口（README 提过 `replay` 命令），闭环只在 DB 里，用户看不到。
→ **修法**：加 `/api/replay/{run_id}` 端点 + 简单回放页，让"零结果→定位→修复→验证"可见。

## 4. 改进路线图（建议顺序）

**阶段一（正确性优先，1-2 天）**
1. 修 `build_embed_text` 字段来源（3.1）—— 直接提升所有 RAG 召回质量
2. 合并 `BadCaseStore`/`DBManager`（3.3）—— 消除重复，降低改 DB 时的双写风险

**阶段二（稳定性，3-5 天）**
3. FAISS → Milvus 迁移（你已验证连通），顺带解决 3.2/3.6/3.8
4. 抽 `LLMClient` 统一客户端（3.4）
5. `VectorStore` / DB 连接池单例化（3.6）

**阶段三（工程化，1 周）**
6. `app.py` 拆 routers + repository（3.5）
7. Agent 异步化 / threadpool（3.7）
8. 面试会话持久化 + health/指标/鉴权（3.9/3.10）
9. README 对齐 + replay UI 闭合（3.11/3.12）

## 5. 一句话结论

架构方向正确（分层清晰、采集可插拔、Agent 有反思防死锁），**主要欠账在"单文件 API 耦合 + 两套重复 DB 实现 + LLM 客户端分裂 + 向量库每次重建"**，以及一处会直接影响召回质量的字段层级 bug。按阶段一→三推进即可，阶段一的 3.1 建议今天就能改。
